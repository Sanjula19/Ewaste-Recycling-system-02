What happened, in order

  1. Verified the toolchain — nothing needed installingArduino IDE 2.3.10 and ESP32 core 3.3.11 both turned out to be the newest releases available. All seven libraries present, and all five handoff sketches compiled clean. CP210x driver already installed; board is COM5 here, not COM8 as on the old laptop.
  2. Read the handoff and found three contradictionsThe load cell is no longer part of Component 4 (only Component 3 has one — weight arrives via the backend), the servos moved to D25/D26, and an IR sensor appeared on D27. None of these are in either PDF.
  3. Wired all three status LEDsGreen D19, yellow D23, red D4, 180 Ω each, sharing one ground column. Verified with a purpose-built LedDebug sketch that blinks all three forever alongside the onboard LED, so a dark lamp can be told apart from a stalled sketch.
  4. IR sensor overheated — removed from the designAlmost certainly reversed VCC/GND. Turned out not to matter: the colour sensor's own Clear-channel drop does the same triggering job, which is what the original design PDF specified all along.
  5. Chased the colour sensor through two pin movesD21/D22 → D32/D33 → finally GPIO 16/17. The giveaway was readings repeating byte-for-byte with Clear lower than R, G and B — physically impossible, so I²C failure rather than darkness. Gain also had to be tuned: 4× was too dim, 60× saturated at 61,442 of 65,535, 16× is right.
  6. Made the backend fast enough for a microcontrollerIngest was answering with 14,362 bytes and taking 14 seconds — past the ESP32's 5 s timeout, so it could never get an answer. Two causes, both fixed. See the next section.
  7. Rewrote the firmware end to endClear-drop trigger with a baseline measured at boot, Wi-Fi POST, JSON parse, LED control. Backed up the old IR version rather than overwriting it.
  8. Sorted the networkLaptop was on SLIIT-STD at 5 GHz — a band the ESP32 physically cannot use, on a different network from the board. Moved both onto the phone hotspot at 2.4 GHz.
  9. Collected the first colour signaturesBrown cardboard and yellow. The result was not what anyone hoped — see the findings below.

The backend fix worth remembering

An ESP32 scan was timing out at HTTP -11. The request was arriving fine; the reply took too long. Two independent causes, each slower than the ESP32's entire patience budget.

CauseCostFix
Response embedded a 90-point forecast series the board can't use14 KB?compact=true → 232 bytes
ARIMA/LSTM model reloaded and backtested every request~6 sCache the model path per metal, 15 min TTL
InfluxDB retried on every call — for a database never started~8 sCircuit breaker: one failure, skip for 60 s

The InfluxDB one was the surprise. Two calls per forecast, each retrying with backoff against nothing, on every single request — and it had been slowing the dashboard down too, not just the terminal. 

first scan after restart   13 s   (TensorFlow load, unavoidable)
every scan after         0.22 s
Warm the backend with one throwaway scan before any demo. The first request after a restart is always slow; everything after it is instant.

Colour findings so far

Materialr/cg/cb/cClear
Copper 4× gain0.5690.2930.248~3,000
Brown cardboard0.5150.2950.197~2,700
Yellow0.5070.3060.177~11,100

Ratios rather than raw values, because raw readings drifted 10× across the day as the light changed while the ratios held to within 0.01. That stability is the whole reason the calibration is worth anything.

Brown cardboard and yellow are 0.008 apart on r/c. Two colours obviously different to the eye are nearly identical to this sensor. What separates them is brightness — Clear differs 4× — but brightness moves with distance and lighting, which is exactly what the ratios were normalising away.

The working conclusion: copper versus not-copper is a question three colour channels can answer. Telling steel from nickel from zinc almost certainly is not, since all four are grey. That is a limit of the sensor, worth stating plainly in the report rather than discovering at the panel.

This is also consistent with the architecture: report §5 gives waste-type identification to Component 3's AI. Component 4's colour sensor is described in the design PDF as detecting object placement and verifying reddish copper — a confirmation aid, not the primary classifier.

ItemScan's decision rule

Colour is used only for the question it can answer reliably, and the answer is sent to the backend as known_material rather than making the server guess from three channels: 

r/c ≥ 0.55 AND b/c ≥ 0.22   →  COPPER      →  yellow lamp
otherwise                      →  NOT COPPER  →  green lamp
The backend's live forecast currently says copper = SELL NOW and aluminium = HOLD — the mirror image of the local rule, so the lamp and the dashboard will disagree. Both verdicts are printed to serial so this is visible rather than mysterious. Setting USE_BACKEND_DECISION = true follows the forecast instead and keeps them in step.

Open issues

  • Weight is a hardcoded 2.5 kg placeholder. No load cell in this component; the real value must come from Component 3 via the backend.
  • IR module overheated and is out of the build. Not blocking — the colour sensor triggers instead.
  • Grey metals probably will not separate by colour. Needs confirming with real samples.
  • Wi-Fi credentials are in the sketch and travel with the folder if it is zipped or shared.
  • The laptop IP changes on every reconnect — re-check ipconfig and update BACKEND_IP before any demo.
  • Bin-full lockout is not enforced in the backend yet, and nothing can clear one.
